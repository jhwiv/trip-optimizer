# Structural validation

The venue verification chain (`concepts/architecture.md`) answers *is this place
real, open, and reachable?* It looks at one venue, or at one pair of adjacent
items, at a time. Structural validation answers a different question: *does the
itinerary as a whole describe a journey a person could actually take?*

The two chains are independent and both run before export.

## Why it exists

A build shipped on 2026-07-28 (an 11-day London → Normandy → Amsterdam → Lisbon
plan) passed every venue check and the expert review, and still contained:

- Day 6 driving to Amsterdam and checking into the Marriott, and Day 7 waking up
  back in Normandy, flying to Amsterdam, and checking into the same Marriott again.
- A header claiming "2+3+2+3 nights" over a day sequence that was 3-2-3-2.
- A restaurant closed on Mondays, booked on a Monday, with a verify note reading
  "this is a Tuesday, confirm open".
- Flight rows whose header time and `depart_time` disagreed by hours.
- A Viator link with a fabricated product ID.
- A regional flight nothing had ever confirmed, presented as fact.

Every one of those is invisible to a per-venue check. Each is trivially
detectable from the plan object.

## The chain

All validators are pure functions over the plan object: no network, no React,
no module state. Each returns flag objects in the shape `placesVerify` already
uses, so both chains share the pre-export gate's vocabulary.

| # | Validator | Module | Emits |
| --- | --- | --- | --- |
| 1 | Day-to-day continuity | `src/dayContinuityCheck.js` | `DAY_CITY_DISCONTINUITY`, `DUPLICATE_CHECKIN`, `ORPHANED_TRANSITION`, `CITY_BACKTRACK`, `VEHICLE_STATE_CONFLICT` |
| 2 | Night arithmetic | `src/legNights.js` | `NIGHT_COUNT_MISMATCH` |
| 3 | Weekday claims in prose | `src/dateFacts.js` (`assertWeekdayClaims`) | `WEEKDAY_CLAIM_MISMATCH` |
| 4 | Flight header vs `depart_time` | `src/flightTimeConsistency.js` | `FLIGHT_TIME_MISMATCH` |
| 5 | Booking-link plausibility | `src/bookingUrlCheck.js` | `BOOKING_URL_IMPLAUSIBLE`, `BOOKING_URL_DEAD` |
| 6 | Flight route confirmation | `src/flightResolver.js` (`findUnverifiedFlights`) | `FLIGHT_UNVERIFIED` |

Severities and blocking behavior are in the flag taxonomy in `CLAUDE.md`.

## Where they run

`applyQualityLayer(plan, inputs)` in `src/App.jsx` calls all six, concatenates
the results, and attaches each flag to its day as `day.structural_flags[]`.
(`day.flags` already exists and holds plain strings — structured flag objects
needed their own field.) Every flag is also echoed into `qc.warnings` so it
shows up in the quality panel.

The pre-export gate in `saveItineraryAsPDF` composes three sources:

```
findBlockingIssues(plan)            // venue-scoped, walks item.flags
findStructuralBlockingIssues(plan)  // structural, walks day.structural_flags
arrivalOrderExportError(plan)
```

No new gating mechanism was added — structural blocks flow through the same
last-line-of-defense that venue blocks always have.

## Two things are not validators

**Auto-correction.** Night counts and weekday claims are *fixed*, not just
flagged: `CLAUDE.md` says day-of-week and sums are computed in code, never
generated by the model, so leaving a wrong value in place with a warning next
to it would be the wrong remedy. The warn exists for visibility into what was
silently changed. Weekday rewriting is deliberately narrow — only
self-referential claims ("today is Monday", "this is a Tuesday") and a
headline's leading weekday. A missed claim is a warn we didn't emit; a
wrongly-rewritten closure note ("closed Mondays" → "closed Tuesdays") would
silently destroy verified venue data.

**Dead-URL stripping.** `BOOKING_URL_DEAD` follows the verify-or-strip
precedent: the URL is removed from the plan object so the PDF stops rendering
it, and the flag records the removal. This happens in a second memo downstream
of `applyQualityLayer`, because the `/api/verify-url` verdict arrives
asynchronously after the quality layer has already run.

## Fixing causes, not just detecting them

Two of the six are safety belts over a fix made at the source:

- `FLIGHT_TIME_MISMATCH` should never fire in practice, because
  `withFlightMerge()` now propagates `flight.depart_time` back to the parent
  `item.time` whenever the resolver writes it. The validator proves the
  invariant holds; a test proves the validator fires when propagation is
  disabled.
- `FLIGHT_UNVERIFIED` replaced the narrower `_timesUnconfirmed` marker, which
  only fired when the model supplied no times. A flight the resolver could not
  confirm is unverified whether or not the model guessed times for it.

## The reviewer is not part of this chain

`buildReviewSystemPrompt` carries a MUST-VERIFY CHECKLIST covering the same six
areas, and `submit_review` accepts an uncapped `structural_findings[]` array so
a structural hit never competes with editorial notes for the 8-finding cap. The
reviewer is a second pair of eyes and stays **advisory** — it does not gate.
The deterministic validators above are what actually block an export. The
2026-07-28 build is the argument for why: the reviewer read that plan and
passed it.
