# Known Issues

Non-blocking issues surfaced during work. Not in the public GitHub issue tracker. Address opportunistically.

## 1. Cloudflare Pages Preview environment is missing API keys

**Severity:** Medium (blocks PR-level live verification)
**Surfaced:** 2026-06-27 during PR #69 verification

**Symptom:** Any PR preview deploy URL (e.g. `https://<sha>.trip-optimizer-6og.pages.dev` or `https://<branch>.trip-optimizer-6og.pages.dev`) returns "Server missing `ANTHROPIC_API_KEY`" the moment the user clicks Build. This is the documented soft-fail path firing — not a regression — but it means **no PR preview deploy can run an actual itinerary build**.

**Root cause:** Cloudflare Pages scopes env vars per environment. `ANTHROPIC_API_KEY`, `PERPLEXITY_API_KEY`, and the `JOBS` KV binding appear to be configured for the Production environment only.

**Impact:**
- PRs cannot be live-verified on their preview URLs
- The "Cloudflare Pages preview" CI check only verifies the static build deployed, not that the app actually works
- 2026-06-27's #64–#69 merges all shipped without preview-level live verification (they relied on CI green + post-merge production verify)

**Fix:**
1. Cloudflare dashboard → `trip-optimizer` → Settings → Variables and Secrets
2. Add `ANTHROPIC_API_KEY`, `PERPLEXITY_API_KEY` as Secrets in the **Preview** environment, mirroring Production
3. Cloudflare dashboard → `trip-optimizer` → Settings → Bindings → add a KV namespace binding named `JOBS` pointing to the same namespace bound to Production, scoped to Preview
4. Re-trigger any open PR's preview deploy to pick up the new bindings

## 2. Wizard date picker is hostile to browser automation

**Severity:** Low (no user-facing impact)
**Surfaced:** 2026-06-27 during PR #69 verification attempt 1

**Symptom:** Browser automation agents repeatedly fail to set a specific date range in the Essentials step's date picker. Behavior observed: typing into the date field doesn't populate it; calendar clicks fire but don't always commit; the displayed range drifts away from the requested values.

**Why it matters:** Any future CI-grade end-to-end smoke test, or any automated QA pass through the wizard, will fail or loop on this step before reaching the results view.

**Possible mitigations (any one is sufficient):**
- Accept typed input in a standard format like `YYYY-MM-DD` and parse it
- Expose stable `data-testid` attributes on the start-date and end-date inputs
- Provide a sensible default range when fields are left untouched, so automation can skip the step entirely
- Add a `?dates=YYYY-MM-DD,YYYY-MM-DD` URL param for deep-linking into a pre-filled wizard

Not urgent. Worth a `chore/` issue if/when end-to-end smoke tests are added.

## 3. Active: PDF intro race condition

**Severity:** Medium (user-facing — affects PR #69's contract)
**Surfaced:** 2026-06-27 user manual verify

**Symptom:** PDF downloaded immediately after Day 1 cards render contains no introduction section.

**Root cause:** After PRs #67 + #69, the introduction is generated by a headless `IntroductionAutoGenerator` component that fires `POST /api/introduction` in a `useEffect` once the build completes. The call takes 5–15 seconds. Nothing gates the PDF download button on `data.introduction` being populated.

**Proposed fix:** Expose `isGenerating` state from `IntroductionAutoGenerator` via a new `onGeneratingChange` prop, lift it to the results view component, and disable the PDF download button (with "Preparing introduction…" label) until `data.introduction` is populated or the generator finishes/errors.

**Status:** Not yet fixed. Branch `fix/intro-race-on-pdf-download` was started locally but never pushed (sandbox was reset).

## 4. PDF generation perf

**Severity:** Low (annoying but not broken)
**Surfaced:** 2026-06-27 user feedback

**Symptom:** `jspdf` + `html2canvas-pro` PDF export takes a long time and can briefly freeze the tab on multi-day luxury itineraries.

**Root cause:** Pre-existing. The PDF chain is fully client-side, runs on the main thread, and processes a lot of layered content (cover, intro, day cards, dining chips, optional by-category view).

**Possible mitigations:**
- Move PDF generation to a Web Worker (significant rewrite)
- Reduce per-page DOM complexity in the canvas-rendered sections
- Show a determinate progress indicator so users know it's working

Not urgent. Worth a `perf/` issue but not a blocker.
