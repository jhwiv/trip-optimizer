## Right-edge clipping on iOS Chrome — root cause: stale WebKit/WKWebView viewport units

**Commit:** (pending — see branch above)
**Files:** `index.html`, `src/App.jsx` (`DateRangeInput`'s popover-positioning effect)

**Symptom:** User repeatedly screenshotted the pre-build "Ready to build" screen and the
build-progress screen with content clipped at the right edge — the Reset button truncated to
"RES", the Plan My Trip button cut off, body text wrapping mid-word. Reproducible on iOS Chrome,
every time, at the start of a build. Self-corrected instantly whenever the user scrolled,
pinch-zoomed, or otherwise interacted with the page ("moved it on the screen to make it drop into
place").

**False lead (see 2026-08-02 investigation, same session, CLAUDE.md "VERIFICATION DISCIPLINE"):**
a near-identical symptom earlier in the same day turned out to be a stuck pinch/double-tap zoom
on one browser tab — confirmed by the user resetting zoom and having it fix instantly. That
diagnosis does NOT hold for this incident: the user was explicit ("There is no issue with my
phone"), it recurred consistently across multiple fresh builds (not one stuck tab), and this
time actual research turned up a citable, official root cause rather than a single anecdotal
data point.

**Root cause, found via web research (not guessed):** WebKit has an officially filed bug
([bugs.webkit.org #170595](https://bugs.webkit.org/show_bug.cgi?id=170595)) where
`window.innerWidth`/`innerHeight`, and by the same underlying mechanism the `vw`/`vh`/`dvw`/`dvh`
CSS units, can report a stale/incorrect value immediately after a page load, resize, or
orientation change — self-correcting only once the browser fires the next reflow (a scroll, a
resize, an orientation change, a zoom gesture). The bug report specifically notes this is **worse
in WKWebView than in Safari's own renderer** — and WKWebView is the engine Apple requires every
third-party iOS browser, Chrome included, to use. A live 2026 Apple Developer Forums thread
(https://developer.apple.com/forums/thread/803987) shows this is still an active, current-iOS
issue for `dvh` specifically.

This repo's `index.html` set `max-width: 100vw; max-width: 100dvw;` on both `html, body` and
`#root` — the two top-level containers everything else renders inside. That's exactly the
mechanism the bug report describes: relying on `vw`/`dvw` for root-level layout width, which is
the value WebKit can serve stale on first paint in WKWebView. `width: 100%` was already set
alongside it in both rules and does not go through the same computation path — it resolves
against the live containing block on every layout pass, so it doesn't have anywhere to go stale.

**Fix:** removed `max-width: 100vw; max-width: 100dvw;` from both the `html, body` rule and the
`#root` rule, keeping `width: 100%` and `overflow-x: clip` (which does the actual horizontal-
overflow-prevention job on its own — `contain: paint` was already removed from `#root` for an
unrelated reason on 2026-08-02, see below, and was never load-bearing for the clip behavior
either).

**Secondary finding, same root cause family:** `DateRangeInput`'s popover right-edge guard
(`src/App.jsx`, the `useLayoutEffect` computing `shiftX`) read `window.innerWidth` directly.
Switched to `document.documentElement.clientWidth`, which the same research identifies as not
subject to the same staleness.

**Verification:** full Playwright end-to-end run (mocked build + review pipeline, same fixture as
the 2026-08-02 build-hero work) against both the dev server and the actual production bundle,
before and after the change — hero screen renders correctly, no scroll jump, date picker popover
still clamps to the viewport correctly at 360px width. Lint baseline unchanged (14 warnings, 0
errors). Full test suite 2799/2799 (one pre-existing, unrelated failure — a Node.js `navigator`
global test-env issue, not a code defect).

**Relationship to the 2026-08-02 `contain: paint` removal:** that fix and this one address two
different bugs that happened to produce similar-looking symptoms (content not where it should be
on screen) via two different mechanisms — `contain: paint` broke `position: fixed` containing-
block resolution; stale `vw`/`dvw` broke root layout width. Both happened to live in the same two
CSS rules in `index.html`, which is why they were found back to back.

**OUTCOME — reported failed by the user, same day:** after this fix shipped, the user tested on
their real device and reported: *"Failed. Quick pinch on screen fixes it but you failed."* The
WebKit #170595 mechanism is real and the fix is legitimate hardening (kept), but it was not the
(or not the complete) cause of the clipping the user is seeing. Do not cite this section as "the
fix" for the clipping symptom — see the follow-up entry below for the next hypothesis attempted.

## Right-edge clipping, attempt 3: iOS auto-zoom-on-focus for sub-16px form fields

**Commit:** `f234bb8`, merged to `master`.
**Files:** `src/App.jsx` — `Inp`, `Autocomplete`, `NarrativeBox`, `Sel`, `TagInput`, plus the
multi-city nights input, share-URL display, revision-day `<select>`, `/find` page's "Show"
dropdown and "Guidelines" textarea, and the "confirm venue names" custom input.

**Context:** the previous two attempts at this same user-reported symptom (`contain: paint`,
documented 2026-08-02, which was a real and correctly-fixed bug but for a different UI defect; and
the vw/dvw fix above, which the user reported as failed) did not resolve what the user is seeing.
Re-audited from scratch rather than assuming either prior diagnosis was adjacent-but-incomplete.

**Root cause candidate (sourced, not guessed):** CSS-Tricks ("16px or Larger Text Prevents iOS Form
Zoom"), GitHub issue `huygn/til#90`, and a GitLab MR titled "Fix iOS input zoom on mobile devices"
all document the same iOS Safari/Chrome behavior: focusing a form field with computed font-size
under 16px triggers the OS to zoom the whole page in, to keep the text legible. This app is a
single-page wizard with no full page reload between steps, so a zoom triggered while typing on an
early step (e.g. the destination field, or the narrative textarea — often the very first thing a
user touches) can persist across every later screen, including the pre-build and build-progress
screens the user screenshotted, until manually pinched back out. This matches the reported
self-correction behavior exactly ("quick pinch on screen fixes it").

Audit found 11 distinct fields/components at 12px–14.5px, covering nearly every text-entry point
in the Details form (via the shared `Inp` and `Autocomplete` components) plus several standalone
fields. Notably, `/find`'s "Location" input was **already** at 16px — an existing precedent for
this exact fix already present in the codebase before this session touched it.

**Fix:** every affected field's `fontSize` raised to `"16px"` (checkbox/radio/file inputs excluded
— they don't trigger the behavior).

**Verification performed:** computed-style check via Playwright (`getComputedStyle(el).fontSize`
returns `"16px"` for every visible field in form mode); `npm run lint` unchanged (0 errors, 14
warnings); `npm test` 2799/2799 (same one pre-existing unrelated failure as before); screenshot of
the form-mode screen confirms no visual regression from the larger text.

**Status: NOT yet confirmed by the user.** This mechanism is deterministic and triggered by a
specific user action (focusing a field), which is a meaningfully different failure mode than the
previous attempt's timing-dependent stale-viewport-unit read — so it's a genuine new candidate, not
a retry of the same idea. But given two prior sourced diagnoses for this exact symptom have already
turned out to be wrong or incomplete, this must not be described as "fixed" anywhere (chat, docs,
or code comments) until the user tests it on their real device and confirms.

## Build-progress card rendering solid white instead of translucent glass

**Commit:** `df9757e`, merged to `master`.
**Files:** `src/App.jsx` (`BuildProgressScreen`)

User screenshot showed the "① Initial build / ② Expert review" progress card as an opaque solid
white block sitting on top of the hero's dark photo backdrop, visually inconsistent with the two
other cards on the same screen ("What's happening" checklist, "Your trip" recap), both of which
already used a frosted dark-glass treatment (`BUILD_HERO_GLASS`: `rgba(0,0,0,0.38)` + `blur(14px)`).

Root cause: the progress-bars card and the "done" checkmark card both used the shared, opaque
`cardStyle` (`background: var(--color-background-primary)`, `#FFFFFF` in light mode) instead of
`BUILD_HERO_GLASS`. Fixed by switching both card sites to `BUILD_HERO_GLASS`, plus a new
`HERO_CARD_VARS` object that locally overrides the CSS custom properties (`--color-text-primary`,
`--color-text-secondary`, `--color-text-tertiary`, `--color-border-secondary`,
`--color-border-tertiary`) the shared `BuildPhaseBars`/`BuildCancelButton` components read — those
components are also used inside the light-card bottom-sheet overlay elsewhere, so their text colors
couldn't be hardcoded; scoping the override onto just this card's div via inline `style` (React
supports arbitrary `--custom-property` keys in the `style` object) makes the same shared components
resolve to the hero's white-on-dark palette here without touching their implementation.

Verified: computed-style Playwright check confirmed `backgroundColor: rgba(0, 0, 0, 0.38)`,
`backdropFilter: blur(14px)`, `color: rgb(255, 255, 255)` on the card during an in-progress build
(mocked `/api/build` held pending); screenshot shows all three cards now reading as one consistent
glass system. Lint baseline unchanged (0 errors, 14 warnings); full suite 2799/2799 (same one
pre-existing unrelated failure).

## Itinerary quality audit — Sedona build (three code bugs, not model quality)

**Commit:** (pending — see branch above)
**Files:** `src/App.jsx` (`applyQualityLayer` §1 restaurant dedupe, §2.6 marquee coverage,
`tonightPriority`/`stripTonightPrefix`)
**Trigger:** user attached a third-party review of a generated Sedona PDF (`trip20260803sedonaaz.pdf`)
flagging: Elote Cafe listed twice on Day 3 (6:30 PM and 7:30 PM, identical restaurant); the Pink
Jeep Broken Arrow tour promised repeatedly in prose (day headline, `tonight[]`, `flags[]`) but never
actually scheduled as a Day 3 item; and MUST-tagged `tonight[]` entries not reading as urgent.
Extracted the PDF's text (`pdfminer.six`, since `pdftotext`/`pypdf`'s crypto backend were both
unavailable in this sandbox) to confirm the exact item shapes before writing any fix.

**1. Same-day duplicate venue (`DUPLICATE_VENUE_SAME_DAY`, new flag, warn, auto-corrected).**
The existing restaurant-dedupe pass (`applyQualityLayer` §1) keyed its "seen" map only by
normalized restaurant name, with no day-of-first-occurrence distinction from day-of-repeat. A
same-day duplicate (both items dated Day 3) and a legitimate later-day return visit hit the exact
same code path — both got annotated `"Return visit — first appeared Day 3 (dinner)"` and *kept*,
which is right for a real return visit two days later and wrong for a same-day duplicate: nobody
eats two dinners at the same restaurant an hour apart, so keeping both (even labeled) still shows
the same restaurant twice in the PDF, which is exactly what the reviewer flagged as confusing.
Fixed by tracking same-day-same-meal-type occurrences separately: the second same-day/same-type
hit is now dropped from `day.items` (first, generally more complete, occurrence kept — in the
Elote Cafe case the second entry was itself truncated, missing hours/closures/backup) and recorded
as a new `DUPLICATE_VENUE_SAME_DAY` warn flag (auto-corrected, so warn not block — same convention
as `NIGHT_COUNT_MISMATCH`/`WEEKDAY_CLAIM_MISMATCH`). Same restaurant, same day, *different* meal
types (e.g. lunch then dinner at the same café) is left alone — that's a legitimate itinerary
choice, not the bug.

**2. Marquee-coverage check split into "scheduled" vs "merely promised" (`applyQualityLayer` §2.6).**
This pre-existing check (`MARQUEE_REQUIRED`) warns when a destination's iconic sights never show up
anywhere in the plan. Two bugs, one masking the other:
  - The haystack it searched read `it.name` and `it.notes` — fields that do not exist on
    `DAY_ITEM_SCHEMA` (items carry the headline in `text` and an optional insider note in `why`).
    The check was effectively blind to almost every item's real content, relying on `day.headline`,
    `day.weather`, and `item.location` alone.
  - Even after fixing that, a single merged haystack still cannot catch "promised but not
    scheduled": the Sedona Day 3 headline literally read *"Pink Jeep off-road tour — broken-arrow
    trail at midday"* and `flags[]` said the tour *"books out 5–7 days ahead — reserve this week"*
    — both would satisfy a merged check regardless of whether an actual item existed, because the
    keyword match doesn't care which field it hit. That's precisely the failure mode reported: the
    model talks about the tour convincingly and then never emits the Activity item for it.

  Fixed by splitting into two haystacks — `itemHaystack` (only `items[].text/why/location` +
  restaurant/hotel names — i.e. things a traveler could actually show up to) decides whether a
  marquee sight counts as scheduled; `proseHaystack` (`day.headline`, `day.weather`, `flags[]`,
  `snobs[]`) is checked only to distinguish two different warning messages: *"promised but not
  scheduled"* (mentioned in prose, no item) vs. plain *"not scheduled"* (never mentioned at all).
  Also added Pink Jeep/Broken Arrow as Sedona's own required marquee group, separate from the
  existing hike/vista group (`cathedral rock`/`bell rock`/`chapel of the holy cross`) — the two
  are not substitutes for each other, and the hike group being satisfied by Bell Rock is exactly
  why the original check never fired for this build.

**3. `tonightPriority`/`stripTonightPrefix` didn't recognize bare "MUST:" or plain-text "Must today:".**
The prompt instructs the model to prefix urgent `tonight[]` entries with the literal `'⚠︎ Must
today:'`, but the model doesn't reliably reproduce that exact phrasing — this build emitted bare
`"MUST: Reserve Pink Jeep Broken Arrow Tour for Day 3…"`. `tonightPriority`'s old regex
(`/^must today/i`) didn't match, so the entry silently fell through to the default styling with
no urgency badge — exactly the entries most needing one. Fixed by also matching bare `"MUST:"`
(colon required, so an ordinary sentence like "Must-see sunset spot" isn't misclassified).

  Separately, and worse: `stripTonightPrefix`'s regex used `⚠︎?` expecting the whole two-character
  emoji sequence (U+26A0 WARNING SIGN + U+FE0E variation selector) to be optional — but a bare `?`
  only applies to the immediately preceding character, so only the *selector* was optional; the
  base glyph stayed mandatory. Any tonight entry that didn't literally start with that exact unicode
  character — i.e. almost all of them, since the model reliably reproduces the *words* "Must today:"
  far more often than the exact emoji — never had its prefix stripped at all, and rendered with the
  raw `"Must today: "` (or now `"MUST: "`) text still attached in the UI/PDF. Fixed by wrapping the
  glyph+selector pair in its own optional group: `(?:⚠︎?\s*)?`.

**Verification:** `tests/test_itinerary_quality_fixes.mjs` (new, 22 assertions, mirrors the three
closures per the `test_day_completeness_and_city_normalization.mjs` convention since
`applyQualityLayer` can't be imported directly) — includes the exact Sedona Day 3 shape as a
regression case for all three fixes. Full suite 2821/2821 (2799 + 22 new; same one pre-existing
unrelated failure). Lint baseline unchanged (0 errors, 14 warnings).

**Scope note:** did not attempt a general "any `tonight[]` MUST-reservation must map to a scheduled
item" validator across all destinations — reliably parsing a proper-noun venue/activity name out of
freeform LLM prose and matching it against item text is inherently fuzzy (unlike the marquee-list
fix above, which checks a small, curated, destination-specific keyword list). That risks false
positives blocking correct plans, which cuts against both `CLAUDE.md`'s "ambiguous classification
falls back to warn" principle and the deterministic-over-heuristic posture this whole validation
chain is built on. The no-confirmed-start-date and spring-vs-August weather-window questions raised
in the same review are separate, unaddressed: the former depends on what the user actually entered
at intake (not obviously a code bug without seeing those inputs), and the latter would need a real
weather-normals source to verify against, which doesn't exist in this pipeline today — flagging
both rather than guessing at a fix per the project's verification discipline.
