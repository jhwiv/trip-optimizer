## Shareable URL feature

**Commits:** `1d97325`  
**Files:** `functions/api/share.js` (new), `functions/s/[id].js` (new), `src/App.jsx`

User asked: "Is it possible to have the web app button converted into a functioning webpage using a generic Cloudflare URL from my account?"

**What was built:**
- `POST /api/share` — accepts `{ plan, inputs }`, generates a self-contained HTML page via `buildWebApp()` (same function used by the client-side "Export as web app" button), stores in Cloudflare KV namespace `SHARES` with an 8-char hex slug and 90-day TTL, returns `{ id, url }`.
- `GET /s/:id` — reads stored HTML from `SHARES` KV, serves as `text/html`. Validates 8-char hex ID format. Returns 404 if expired or not found.
- UI: "Get shareable link" button added alongside the download button. When clicked, posts to `/api/share`, shows a read-only URL field + Copy button + "expires in 90 days" note.

**Production prerequisite not yet done by user:** A `SHARES` KV namespace must be created in the Cloudflare dashboard and bound as `SHARES` in Pages environment settings. Without this binding, the endpoint returns 503.

## Activity count — extended classifier

**Commit:** `35457ed`  
**File:** `src/activityCountConstraint.js`

User reported: "I asked for 2 activities and got 7 on last build. This is persistent."

Root cause: `TRIP_TOTAL_PATTERNS` in the classifier only matched the original explicit phrasings ("N activities total", "just/only N", "for the trip"). Natural-language variants like "I want 2 activities" or "give me 2 activities" slipped through → no hard cap injected → model used per-day pacing defaults.

**Fix:** Added 5 new pattern groups:
- "a total of N activities"
- "N activities max/maximum/tops"
- "limit/keep/cap (to/at) N activities"
- Verb-prefixed: "want/need/prefer/include/plan/schedule N activities" with negative lookahead excluding per-day qualifiers
- "give me N activities" with same negative lookahead

15 new test cases verified. See `concepts/activity-count.md` for full technical record.

## Activity count — default pacing hardened

**Commits:** `e5d9e22`, `67abd8e`  
**File:** `src/App.jsx`

User reported a plain "4 nights in Savannah" build producing 13 activities.

Root causes:
1. `Pace: No preference` (when no pace selected in narrative mode) → model defaulted to ~3 activities per full day
2. MARQUEE SIGHTS rule forced 6 Savannah landmarks as mandatory Activity items, stacking on top of the pacing default

**Fixes:**
1. User prompt now sends `Pace: Relaxed (1 activity/day) — traveler did not specify; use this conservative default` when pace is unspecified.
2. Pacing rule rewritten with explicit per-pace caps: Relaxed = 1/day, Moderate = 2/day, Full = 3/day. Marquee sights count toward the limit, not on top of it. Arrival/departure days = 0–1 regardless.

**Remaining gap:** The MARQUEE SIGHTS rule uses `MUST` language that outranks the pacing caps. Charleston with 6 marquees and Relaxed pace (1/day = 3 total) still produces more than 3 activities because the MUST overrides. Fix: add yield clause to MARQUEE rule stating it defers to the pacing cap. **Not yet implemented.**

## Layout — horizontal page offset on mobile (iOS)

**Commit:** `25bd571`  
**File:** `src/App.jsx`

User screenshot showed the entire page content shifted right, with left-side content clipped ("RAVEL PLANNING" instead of "TRAVEL PLANNING").

Root cause: When the build starts, `progressPanelRef.current?.scrollIntoView({ behavior: "smooth", block: "start" })` fires. On iOS Safari, `scrollIntoView` without an `inline` constraint also adjusts horizontal scroll to bring the element fully into view — even when `overflow-x: hidden` is set on `html/body`. This shifted the visible viewport right.

**Fix:**
- Added `inline: "nearest"` to the `scrollIntoView` call — prevents any horizontal scroll adjustment.
- Added `left: 0` to every `window.scrollTo({ top: 0 })` call (9 call sites) — guarantees horizontal position is reset on every scroll-to-top.
