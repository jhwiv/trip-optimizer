## PDF export false-positive block on a correct 14-night, 5-city itinerary — `DAY_CITY_DISCONTINUITY`

**Files:** `src/dayContinuityCheck.js`, `tests/test_day_continuity_check.mjs`

**Symptom:** User reported "Big two week build. PDF failed, save failed. Shareable link failed."
for a real London → Cambridge → Normandy → Nuremberg → Porto (14-night, 5-city) build. Only the
"Export as web app" (HTML) path succeeded, which made it possible to extract the real plan JSON
from the user's own successful export and reproduce the failure exactly, without needing to
simulate chunk-mode building.

**Reproduction:** live Playwright run against the real plan (pre-seeded into `localStorage` and
opened via the app's existing "Open saved trip" path, bypassing the build pipeline) surfaced the
exact PDF pre-export gate error:

```
Cannot export: 1 blocking issue — 0 venue verification, 1 itinerary structure —
Day 9: Nuremberg, Germany (DAY_CITY_DISCONTINUITY). Re-run the build or remove the
affected items before exporting.
```

**Root cause — two compounding bugs, both in `dayContinuityCheck.js`:**

1. **Comma-qualifier route text defeats the destination match.** Day 8's Flight item read `"Fly
   Paris CDG → Nuremberg, nonstop"`. `parseRoute` splits on the arrow, giving a destination token
   of `"Nuremberg, nonstop"` — which is neither a substring of nor a superstring of the canonical
   city name `"Nuremberg, Germany"`, so `resolveCity` never matched it. The `flight.to_airport`
   fallback (`"NUE"`, an airport code) isn't in the canonical city list either. Net effect:
   `leg.transitions` stayed empty for Day 8.

2. **`canonicalCities()` fed itself a transit day's own arrow-formatted label as a "city name."**
   Independent of (1): every `days[].city` was added to the canonical resolution list verbatim,
   including transit-day labels like `"Normandy → Nuremberg"` (the documented `DAY_SCHEMA`
   convention for a travel day). `norm()` only trims and lowercases — it does not strip arrows or
   spaces — so the raw string `"normandy → nuremberg"` *contains* `"nuremberg"` as a literal
   substring. Canonical names are tried longest-first so shorter, more specific names win over
   accidental superstrings; `"Normandy → Nuremberg"` (21 chars) sorted ahead of the real
   `"Nuremberg, Germany"` (19 chars) and satisfied `resolveCity`'s substring check first. So once
   bug (1) was fixed and `"Nuremberg"` (comma-stripped) became a resolvable candidate, it resolved
   to the *transit label itself*, not the real city — `leg.transitions[0].to` became `"Normandy →
   Nuremberg"`, identical to Day 8's own raw city field, so the day's *resolved ending city* was
   still not `"Nuremberg, Germany"` and the discontinuity check kept firing.

   A third, smaller issue compounded both of the above: `DAY_CITY_DISCONTINUITY` (check #1 in
   `findContinuityIssues`) compared the *previous day's raw `city` string* directly against the
   next day's `city` string. For a transit day this raw string is an arrow-formatted label by
   design — it will essentially never string-equal a plain destination name even when the days are
   perfectly continuous, independent of the resolution bugs above.

**Fix (three changes, all required together):**

- Added `beforeComma(s)` and used it as an extra fallback candidate in `itemDestination`'s
  `firstResolvable([...])` calls, so `"Nuremberg, nonstop"` also offers `"Nuremberg"` as a
  candidate.
- `canonicalCities()` now skips any `days[].city` that contains an arrow (`→`, `->`, `—>`, `–>`)
  when building the resolution list — a transit-day label is never a legitimate "canonical city"
  to match free text against, only a real destination name is.
- Hoisted a `dayEnd` computation (each day's actual *resolved* ending city — the destination of
  its last transition, falling back to its own `city` field) to the top of `findContinuityIssues`,
  and changed the `DAY_CITY_DISCONTINUITY` check to compare `dayEnd[i-1]` instead of the raw
  `city` string of the previous day. (A pre-existing, functionally-identical `dayEnd` computation
  already existed lower in the same function for the `CITY_BACKTRACK` check — that duplicate
  declaration was removed in favor of the shared, hoisted one.)

**Verification:**
- Standalone debug script (`buildDayLegs`/`findContinuityIssues` imported directly against the
  real extracted plan JSON) confirmed zero issues after the fix, versus the exact
  `DAY_CITY_DISCONTINUITY` block before it.
- `npm run lint`: 0 errors, 14 warnings (unchanged baseline).
- `npm test`: 2913 passed, 0 failed across 75 suites (up from the prior 2910/0 baseline — three
  new regression cases added to `test_day_continuity_check.mjs` for this exact scenario); the one
  pre-existing, unrelated `test_save_pdf_share_first.mjs` failure is unchanged.
- Live Playwright run against the actual dev server, with the real 15-day plan loaded via the
  saved-trip path: clicking "Save as PDF" now fires a genuine browser `download` event
  (`trip-2026-08-04-london-cambridge-normandy-nuremberg-port.pdf`) with no blocking-issue banner —
  versus the pre-fix run, which threw the `Cannot export` error and produced no download.

**Not yet conclusively diagnosed from the same user report (at the time):** "Save trip" and

## Build screen showed only the first city on a multi-city trip

**Files:** `src/App.jsx` (new `basicsDestinationLabel`, five call sites)

User report: "Build shows only one city when there are many." Five separate spots computed a
human-readable "what's building" label the same wrong way: `basics.destination || basics.cities[0].name`.
`basics.destination` is a single string that's only reliably kept in sync with `basics.cities[]` by
the structured city-editor's own `updateCity`/`addCity` handlers — a trip restored with `cities[]`
populated some other way (e.g. a saved entry, or the `ACTIVE_JOB_KEY` persist path) can have
`destination` empty while `cities[]` holds every leg. Falling back to `cities[0].name` in that case
silently dropped every city after the first; falling back to nothing at all (two of the five sites
had no cities fallback whatsoever) printed "Destination not set" for a fully-specified 5-city trip.

Fixed with one shared helper, `basicsDestinationLabel(basics)`, that joins all city names with
" → " (matching the format a built plan's own `destination` string already uses) when
`basics.destination` is empty — applied to `BuildProgressScreen`'s headline, the two
`ACTIVE_JOB_KEY`-persist call sites (so the `ResumeBuildBanner` and resume messages also show every
city), the step-1 "Your trip" recap card, `BuildAndReviewOverlay`'s destination prop, and
`SavedTripsPanel`'s per-row label. Verified live via Playwright: seeded a saved trip with 5 cities
in `basics.cities[]` and an empty `basics.destination` (the exact bug precondition), opened it, and
confirmed both the narrative-mode and form-mode "Your trip" cards changed from "Destination not
set" to "London → Cambridge → Normandy → Nuremberg → Porto" — all five cities, not just the first.

## Night math (`legNights.js`) trusted the day's own city label on transit days

**Files:** `src/legNights.js`, `tests/test_leg_nights.mjs`

An independent PDF review of a rebuild of the same London/Paris/Normandy/Porto trip caught the
meta line ("3+3+2+6 nights") disagreeing with the per-city list ("4+2+3+4" = 13, not even
internally consistent) and with the real day-by-day schedule (correctly: London 4 / Normandy 2+1 /

parenthetical form; `deriveLegNights` now reattributes a transit day's night to the following
day's city — but only when that following day is itself settled, since the trip has two
single-night transit days back-to-back (Normandy → Porto) and naively chaining the reattribution
forward through both would have silently deleted the one-night Normandy stay entirely. Confirmed
live via `applyQualityLayer`: Quality Check banner shows "Recomputed meta night breakdown... →
'4+2+3+1+4 nights'; Recomputed Paris nights 2 → 3" — matching the reviewer's independently
hand-computed answer exactly. 14 new regression tests, full suite 2937/2937.

## The fix above broke large-trip builds the same day — a display hint landed in a field that also drives token-budget math

**Files:** `src/App.jsx` (`basicsDestinationLabel`/`basicsDestinationList`, the "Build from this"
merge), `tests/test_destination_label.mjs`

Minutes after the fix above shipped, a live screenshot showed the SAME "England"-only hero PLUS a
new, worse failure: `No day-by-day plan returned... Got keys: destination, meta, cities` — a real
14-night, 4-country build producing zero day content. Full root-cause writeup is `CLAUDE.md`'s
"KNOWN FAILURE MODE #12" — the `__BUILD_ID__` embedded in the error message (stamped from `git
rev-parse --short HEAD` at build time specifically so a screenshot can be matched to a commit)
confirmed this was live production code, not deploy lag.

Root cause: writing the extracted multi-stop list into `basics.cities[]` (with blank per-city
nights, since extraction can't know the split) silently flipped `isMultiCity` true elsewhere in the
file, which switches the build's night-count math from `basics.nights` to SUMMING
`cities[].nights` — an all-blank sum is 0, collapsing a real 14-night trip's token budget to a
1-night one. The model, still driven by the full narrative (always the true source of truth,
independent of extraction), wrote toward the real 14-night trip while budgeted for 1, truncating
immediately — before any `days[]` content.

Fixed by moving the extracted stop list into a NEW, genuinely display-only field
(`basics.multiStopHint`) that nothing outside the two label functions reads — `basics.cities[]` is
untouched beyond its pre-existing single-entry mirror, so it structurally cannot affect
`isMultiCity` or night math again. Confirmed live via Playwright: captured the actual `/api/build`
request bodies for the exact reported shape — 5 correctly-sized requests (3 chunks + wrapper +
review) fired instead of one truncated single call; re-verified the display fix still works
through the new field. `test_destination_label.mjs` rewritten with a `computeNightsNum` helper that
asserts the regression numerically (14→1 with the buggy shape, 14→14 fixed), 22 assertions.

The lesson: a field read by multiple, unrelated consumers (here `basics.cities[]` — the multi-city
form, the build's night math, and briefly a display label) isn't safe to repurpose for one
consumer's convenience without auditing every other reader's assumptions about what populates it.
