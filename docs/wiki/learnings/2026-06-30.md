## Lessons reinforced

- **Trust git blame over memory.** When accused of reverting a fix, the first move is a static audit (`git log --oneline <fix-sha>..HEAD`, `git blame` on anchor lines, grep the live bundle for signature strings). Don't defend without evidence.
- **A user-reported regression isn't always a code revert.** Same code can produce different symptoms on different inputs. State the actual failure mode (which path bailed, what was empty) before proposing a fix.
- **When the wiki diagnosis is wrong after reading code, STOP and surface the revision as a question.** Don't ship a fix that solves an imaginary bug. See the #24 lesson and the #6 set-aside as twin examples.
- **Verify lost-branch claims before redoing the work.** `git ls-remote`, `gh run list`, `gh pr list --state all` with search terms. Don't trust prior-session "it was pushed" claims.
- **One PR per item. CI green locally before push. Bundle-string grep on the live URL after every merge.** Include regression-guard greps for prior PRs' signatures in the same check.
- **One Computer thread per repo at a time.** Parallel threads produce silent wiki contradictions and duplicate work.

### Peer-review discipline (new this session)

After the flight-number diagnosis I asked the user to peer-review before writing code. Found three things in the review that the initial diagnosis missed:
- `applyQualityLayer` clones items — the strip nulls the CLONE, not `rawData`. Resolver looks at `rawData` and sees a complete flight, so it doesn't help; render uses `data` with the nulled clone. The two paths operate on different objects and never reconcile. (Initial diagnosis said "strip nulls rawData" — wrong.)
- Possibility A: a parallel root cause where `parseDayLabelToISODate` or `normalizeAirportCode` returns null and silently drops the flight from `targets[]`. Same user-visible symptom, different mechanism.
- The fix had to cover BOTH the verify path AND a `verifyTrustOnly` precondition-failure path so that EVERY flight with a number gets `_scheduleVerified` written before the strip runs.

**Lesson:** any structural diagnosis benefits from one round of adversarial peer review BEFORE coding. The review caught two failure modes the initial diagnosis would have shipped without covering.

### Both fixes are the same architectural pattern

Both PR #111 and PR #112 implement "belt + suspenders":
- **Belt** (pre-build): make the prompt rule's enforcement deterministic. PR #111 = universal verify mode against `/api/flights-search`. PR #112 = deterministic regex classifier injecting a machine-readable hard cap.
- **Suspenders** (post-build): enforce the contract in code regardless of what the model did. PR #111 = `_scheduleVerified` + `_verifyTrusted` flags ensure the strip never nulls a real number. PR #112 = `enforceTripTotalActivityCap` trims excess Activity items in `applyQualityLayer`.

This is the pattern future similar recurrences should follow. "No rental car requested but model emitted one," "vegetarian only but model surfaces a steakhouse," etc. — all are the same shape and the same two-layer fix.
