## Active investigation: flight numbers and times missing — NOT a code revert

User reported "flight numbers and times are not listed in the build or in the PDF. This needs careful study to figure out why it gets fixed and then somehow it gets reverted which means you did it without being told to."

**Static audit (this session):** every commit since PR #84 (the #12 fix, `471d969`, 2026-06-29) was audited; none touched flight-pipeline lines. `git blame` on every anchor line traces to PR #84. The live www.routesmith.ai bundle (`index-B_4BBtOR.js`) and the PDF chunk (`itineraryPdf-BxiG8Teg.js`) both contain `_scheduleVerified`, `_autoResolvedFlightNumber`, `flights-search`, and the "scheduled operating flight" qualifier. **The code is intact in master and on the live deploy.**

**The bug is real, but it's not a regression.** Symptom confirmed by user: "both number AND times missing." Two gaps PR #84 did NOT cover:

1. **Schedule API miss.** When `/api/flights-search` returns no candidate for the route+date+airline combo, the resolver silently bails (intentional resilience). Flight stays bare in UI and PDF.
2. **Model emits number but no times.** Line ~6469: `if (fl._userSuppliedFlightNumber || hasNum) return;` short-circuits the resolver when the model already emitted a number. If the model emitted a number but NOT times (instructed not to fabricate), the resolver never tries the schedule API to backfill times.

Build-to-build variance in which gap fires explains the "fix gets reverted" feel — same code, different inputs.

User authorized "repro first, then ship." Sandbox dropped before the API-probe could run. Investigation handed off to the next thread. See `handoff.md` Active Investigation section for the plan.

## Lessons reinforced

- **Trust git blame over memory.** When accused of reverting a fix, the first move is a static audit (`git log --oneline <fix-sha>..HEAD`, `git blame` on anchor lines, grep the live bundle for signature strings). Don't defend without evidence.
- **A user-reported regression isn't always a code revert.** Same code can produce different symptoms on different inputs. State the actual failure mode (which path bailed, what was empty) before proposing a fix.
- **When the wiki diagnosis is wrong after reading code, STOP and surface the revision as a question.** Don't ship a fix that solves an imaginary bug. See the #24 lesson and the #6 set-aside as twin examples.
- **Verify lost-branch claims before redoing the work.** `git ls-remote`, `gh run list`, `gh pr list --state all` with search terms. Don't trust prior-session "it was pushed" claims.
- **One PR per item. CI green locally before push. Bundle-string grep on the live URL after every merge.** Include regression-guard greps for prior PRs' signatures in the same check.
